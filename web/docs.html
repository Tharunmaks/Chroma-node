Getting started

Chroma is one Node.js package (Node 22.5+, which ships SQLite) containing the platform server, the chroma CLI, the Helix 3D engine and the Pyre compiler.

npm i -g github:Tharunmaks/Chroma-node

chroma server                 # start the platform on http://127.0.0.1:3000
# open http://127.0.0.1:3000/dashboard and create an account

chroma init my-site           # Helix starter: a 3D page, a Pyre shader and a Pyre Function
cd my-site
chroma dev                    # http://localhost:5173 — live reload, Pyre compiled on the fly
chroma login                  # stores an API token in ~/.chroma/config.json (mode 600)
chroma deploy                 # → http://127.0.0.1:3000/p/my-site/

Prefer clicking? In the dashboard, New project → Helix starter deploys a live 3D site in one step, and you can drag a folder onto a project to deploy it. The playground deploys a shader with one button.

Deployments

A deployment is an immutable snapshot of your files. Files are stored once by SHA-256, so redeploys only store what changed. Every deployment has a preview URL; a project's production URL points at one of them.

URLServes
/p/<project>/Production
/d/<deployment-id>/One specific deployment (preview)
https://<project>.<CHROMA_DOMAIN>/Production, when the server runs with CHROMA_DOMAIN

Routing

/about serves about.html (clean URLs), folders serve index.html, and a missing file serves your 404.html with status 404. Configure with chroma.json:

{ "name": "my-site", "cleanUrls": true, "spa": false }

spa: true serves index.html for unknown paths without a file extension.

The Pyre build step

Every .pyre file is compiled. shaders/lava.pyre produces shaders/lava.glsl, shaders/lava.wgsl and shaders/lava.pyre.json (metadata: uniforms, buffers, WGSL uniform layout). A compile error marks the deployment ERROR and production is left untouched — read the build log in the dashboard or the CLI output.

Limits

2,000 files, 10 MB per file, 50 MB per deployment, 50 projects per account; the newest 30 deployments per project are kept (production is never pruned). Hidden files and node_modules are skipped; add patterns to .chromaignore.

Pyre Functions

A @kernel inside api/ becomes an HTTP endpoint of the production deployment: api/saxpy.pyre → POST /api/fn/<project>/saxpy; nested folders work too (api/math/fft.pyre → …/math/fft).

# api/saxpy.pyre
uniform a: float
buffer x: [float]
buffer y: [float]

@kernel(64)
fn saxpy(id: int):
    y[id] = a * x[id] + y[id]
POST /api/fn/my-site/saxpy
{ "uniforms": { "a": 2 }, "buffers": { "x": [1, 2, 3], "y": [10, 10, 10] }, "count": 3 }

200 { "buffers": { "x": [1, 2, 3], "y": [12, 14, 16] }, "ms": 0.4 }

Buffers are arrays of numbers or a length (zero-filled). count (threads) defaults to the longest buffer. Each call runs in a fresh worker thread with a 3 s timeout, a 96 MB heap, a 20M-iteration loop budget and at most 1M buffer elements. CORS is open so deployed pages can call their functions.

JS server functions

Any api/*.js file that export defaults a handler becomes an endpoint at /api/fn/<project>/<name> (any HTTP method). Handlers get the request and your project's database:

// api/guestbook.js
export default async function (req, { db }) {
  // req: { method, path, query, headers, body }   (body is parsed JSON when sent as JSON)
  if (req.method === 'POST') {
    const doc = await db.collection('guestbook').add({ message: String(req.body.message).slice(0, 280) });
    return { status: 201, json: doc };
  }
  const { docs, total } = await db.collection('guestbook').list({ order: '-_created', limit: 10 });
  return { json: { total, docs }, headers: { 'Cache-Control': 'no-store' } };
}

Return { status, json }, { status, body, headers }, or any plain value (sent as JSON). db.collection(name) offers list(query), get(id), add(doc), set(id, doc), update(id, partial) and remove(id), with owner rights. console.log output is captured.

Isolation: every request runs in a fresh child process with Node's permission model (no filesystem, subprocesses, workers or native addons), code generation from strings disabled, and a separate V8 context that talks to the host only through JSON strings, so no host object is reachable. Limits: 5 s, 64 MB heap, 200 database calls, 1 MB response. Functions cannot set cookies or security headers, and have no network access. Admins can disable JS functions with ALLOW_JS_FUNCTIONS=0.

Database

Each project has JSON document collections (SQLite underneath). Create them in Dashboard → project → Database, set rules, browse and edit documents.

RuleValues
readpublic (anyone can list/get) · private (owner only)
writepublic (anyone can add/edit/delete) · create (anyone can add, nobody can edit — forms, guestbooks) · private

Public endpoints for deployed pages (CORS-enabled): GET/POST /api/db/<project>/<collection>, GET/PUT/PATCH/DELETE …/<id> and GET …/stream (Server-Sent Events: add, update, delete, clear). Queries: where=field:op:value (ops eq ne gt gte lt lte contains, repeatable), order=field or -field (also _created, _updated), limit (≤ 100), offset. Sending your API token as Authorization: Bearer chr_… bypasses the rules (server-to-server). Limits: 50 collections, 10,000 documents each, 16 KB per document; field names may not start with _.

Analytics

Requests to a project's production URL are counted on the server: page views (HTML and 404s), unique visitors, referrers (host only), device class, status codes, response time, function calls, database calls and custom events. Visitors are an HMAC of IP + user agent + project with a salt that rotates daily, so no cookies or raw IPs are stored; bots are excluded from visitor counts. Data is kept 31 days.

The dashboard's Analytics tab streams every hit live (GET /api/projects/:name/analytics/stream, SSE) and summarises 1h, 24h, 7d or 30d (GET /api/projects/:name/analytics?range=24h). Send custom events from your page with POST /api/a/<project>/event {"name": "signup"} or the SDK.

Pyre language

Pyre is a statically typed GPU language with Python-style syntax. A file compiles to GLSL ES 3.00 (WebGL2), WGSL (WebGPU) and JavaScript (CPU); Pyre's npm run gpu-check renders every example on real WebGL2 and WebGPU drivers and compares the result with the CPU backend pixel by pixel.

# A complete fragment shader
uniform time: float
const SPEED = 2.0

fn wave(p: vec2) -> float:
    return sin(p.x * 10.0 + time * SPEED) * 0.5 + 0.5

@fragment
fn main(uv: vec2) -> vec4:
    var col = vec3(uv, 0.5) * wave(uv)
    col.r += 0.1 if uv.y > 0.5 else 0.0
    return vec4(col, 1)

Types & values

TypeNotes
bool, int, float32-bit. Integer maths wraps like the GPU; / truncates.
vec2 vec3 vec4Float vectors. Swizzle with xyzw or rgba: v.zyx, c.rgb. Assign one component: v.x = 1.0.
mat2 mat3 mat4Column-major. m * v, v * m, m * m, m[i] is a column.
[float], [int]Buffers (kernels only): buffer data: [float].

Declarations: uniform name: type, buffer name: [float], const NAME = expr, let (immutable) and var (mutable) with inferred or annotated types (let r: float = 1). Ints are promoted to floats wherever a float is expected, so vec3(1, 0, 0) just works. Operators: + - * / % **, comparisons, and or not, int bitwise & | ^ << >>, compound assignment, and Python's a if cond else b.

Control flow

for i in range(8):            # also range(start, end) and range(start, end, step)
    if i == 2:
        continue
    elif i > 6:
        break
var n = 0
while n < 100 and dot(z, z) < 4.0:
    n += 1

Functions are typed (fn f(x: float, y: vec2) -> vec3:), may be declared in any order, cannot recurse (GPUs have no call stack) and must return on every path. The compiler reports the line and column of every mistake and suggests fixes for typos.

Entry points

DecoratorSignatureTargets
@fragmentfn main(uv: vec2, frag: vec2, normal: vec3, position: vec3) -> vec4 — take any subset of the inputsGLSL, WGSL, JS
@kernel(n)fn k(id: int); n is the workgroup size (default 64)WGSL, JS

uv is 0..1 (origin bottom-left), normal is the view-space normal (normal.z ≈ 1 facing the camera), position the object-space position, frag the pixel coordinate (its y axis follows each platform's convention). In Helix, time, resolution and mouse uniforms are fed automatically.

4D models are Polytope4D objects: vertices rotate in the six planes xy xz xw yz yw zw and are projected into 3D every frame. In the studio you can also write your own model in Pyre: fn surface(u: float, v: float) -> vec3, or surface4 -> vec4 for 4D.

Security model

  • Accounts. Passwords are hashed with scrypt (N=215, r=8, p=1, random salt) and compared in constant time. Unknown users cost the same time as wrong passwords. Five failures lock an account for 15 minutes; auth endpoints are also rate limited per IP.
  • Sessions. 256-bit random tokens in HttpOnly; SameSite=Strict cookies (Secure with CHROMA_HTTPS=1), 7-day expiry. Only SHA-256 hashes are stored. Every cookie-authenticated write needs the session's CSRF token; login and signup reject foreign Origins. Changing your password signs out other sessions.
  • API tokens. Shown once, stored as hashes, revocable, with last-used tracking.
  • Platform pages. Strict CSP (script-src 'self' plus the hash of the import map, no inline styles, no eval), frame-ancestors 'none', COOP, CORP, nosniff, Referrer-Policy and Permissions-Policy. The only script allowed to evaluate generated code is the Pyre CPU worker, which has its own CSP with no network access.
  • Deployed sites. Every file is served with Content-Security-Policy: sandbox …, so deployed pages (and uploaded SVGs) run in an opaque origin: they cannot read platform cookies, call the authenticated API, or script the dashboard, even on the same host.
  • Uploads. Paths are validated (no traversal, absolute paths, backslashes, control characters or hidden files), sizes are capped, JSON bodies are size-limited, and storage is content-addressed.
  • Functions. Pyre has no strings, I/O or recursion, and its JS output can only touch its own values. Kernels run in fresh worker threads with time, memory, loop and buffer limits. JS functions run in a fresh, permission-restricted child process with code generation disabled and a string-only bridge (see JS server functions).
  • Database. Per-collection rules, parameterised SQL with validated field names, size limits, rate limits per IP; private collections are never readable from deployed pages.
  • Analytics. No cookies, no raw IPs; visitor hashes use a salt that rotates daily; 31-day retention.
  • Audit log. Sign-ins, failures, lockouts, tokens, projects and deployments are recorded per account (Dashboard → Security).
